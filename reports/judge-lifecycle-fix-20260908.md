# Judge 进程管理诊断与修复

## 已确认的问题

完整 conv-30 小批 `priority-full-conv30-20260908-02` 已完成 19 个会话、369 条消息的 27 次写入，写入零失败；6 题均完成检索与回答，但全部发生 judge_error。运行清单仍配置固定 `http://127.0.0.1:8766/v1`，检查时该端口拒绝连接、原适配器 PID 48793 已消失。

此前适配器由独立临时 Python 启动器以后台进程启动，只有一个 PID 文件，未纳入 experiment runner 的 ManagedRun 子进程。runner 只监督服务与评测器，既未负责启动 Judge，也未在长时间灌入期间检查 Judge 是否存活。适配器还关闭了请求日志，且没有退出事件记录。

现有证据不能确定原进程由谁终止，不能断言是 OOM、休眠、会话清理或特定系统行为。确定的设计缺陷是必需依赖的进程归属、启动预检与运行监督缺失。

## 修复

- `run-experiment.py --upstream-judge` 在启动服务前，通过 `judge_runtime.py` 自行启动本批次专用 Judge。
- 操作系统分配本地端口，ready 文件在绑定后发布；校验健康接口的 PID，不占用或接管其他任务的固定端口。
- 使用原始上游 bridge 与 Qwen3:14b 做真实小型预检，通过后才开始灌入。题目、参考答案及历史预测不参与预检。
- Judge 标记为必需子进程；运行时每次 poll 检查退出，异常退出保存退出码并停止本批次其他进程。只操作自身持有的 Popen，不依靠旧 PID 杀进程。
- 正常收尾由 runner 清理其 Judge。适配器新增健康身份、请求失败类型及 SIGTERM/SIGINT/停止事件；SIGKILL 无法由进程自身记录，由父进程保存 -9。
- 上游 Judge 源码、提示词、Qwen 推理参数保持不变，未改写历史记录或给旧批次补分。

## 验证

- 新增进程死亡检测与独立端口/信号日志测试，修复前失败、修复后通过。
- 总控 runtime 与 Judge lifecycle 测试：12/12。
- 评测器回归：Node 24/24、Python 17/17，共 41 项。
- 真实 Qwen bridge 和 embedding 预检通过；同时确认两个模型驻留。
- 随后受控 SIGKILL 本次诊断 Judge，父进程检测到 -9、记录失败，并停止自己的模拟评测子进程。该诊断没有运行基准题，也未修改保存答案。

真实诊断结果见 `reports/judge-lifecycle-diagnostic-20260908.json`；评测器回归输出见 `reports/judge-lifecycle-eval-tests-20260908.txt`。
