# 查询矩阵执行与真实重试观察

## 有限查询执行器

新增 `scripts/run-query-suite.py` 与 `scripts/query_suite.py`，按现有显式计划执行 sources/rerank/coverage/events/conditional 的三次查询重复。sources 首轮作为已完成灌入来源，因此剩余14个串行任务，每个任务包含两个基准；连同来源共30次基准运行。

默认仅输出可审阅计划。`--execute` 才会启动子任务，并逐项检查：

- 计划与实验 spec 的配置名一致，比较关系完整有效；配置差异只能使用支持的检索设置，不能夹带写入模型、生命周期或最终证据预算变更。
- 两个来源运行均结束，全部题号/数据哈希/背景身份有效；当前 service/eval 源码干净且 commit 与来源相同，原 spec 和 Answer/Judge 一致。
- 独立比较工具验证原 HTTP 审计未过期、全部计划 add 已成功、共享 namespace 与写入身份匹配。仅存在 finished 标记不能替代完整写入证据。
- 已完成的查询配置必须逐项匹配预期服务设置，并通过配对来源验证。仅完成一个基准、运行中、损坏或仅遗留服务配置的任务均拒绝，不能静默跳过或重启。
- 每个子任务结束后重新验证；非零退出立即停止。完整题目中的服务、答案或判分错误仍保留，子进程退出零不代表答案质量通过。
- 同一 campaign 使用操作系统文件锁，避免两个执行器同时调度。锁文件存在本身不是活跃进程证据；只有实际锁占用才表示并发执行。

运行示例（新输出目录必须不存在）：

```sh
python3 scripts/run-query-suite.py \
  --campaign CAMPAIGN \
  --plan configs/round2-query-comparisons.json \
  --spec configs/round2-resilient-source-quality.json \
  --comparison-tools artifacts/round2-eval-human-calibration \
  --output artifacts/NEW-SUITE-REPORT
```

准备好完整灌入和最终 HTTP 审计后，使用新输出目录及 `--execute` 执行。指定数据覆盖路径时，必须与灌入时的参数和精确数据一致。当前冻结 eval 尚未合入比较工具，因此示例显式从独立候选读取工具；不修改主 eval 的运行身份。

验证：11项执行器测试、4项写入身份测试通过。顺序执行、完成后重查、子任务失败停止及并发锁由受控子进程桩验证。对当前 `round2-resilient-bfec674-dev-r1` 真实执行 `--execute`，在来源仍运行的前置检查处拒绝，启动任务数为0。见[验证摘要](../reports/round2-query-suite-preflight.json)。真正的查询矩阵尚未启动；该来源已存在失败灌入，完成后仍不能用于质量消融。

## B05 第18段的真实重试

本轮只读取已有日志与 SQLite 回执，没有新增模型诊断调用。[证据](../reports/round2-B05-bfec674-real-retry.json)显示：

- 同一 `/add` 请求尝试两次，请求体完全一致；第一次约90.0秒失败，第二次约84.2秒成功。
- 两次 HTTP 尝试中，repair 阶段均经历两次 `UND_ERR_SOCKET` 连接失败，第三次成功。各自 trace_id 内 system/input 完全一致，未通过重写输入或增加语义投票恢复。
- 第一次 HTTP 尝试即便 repair 已恢复，后续 source_erasure 仍耗尽模型时间，返回 MODEL_OUTPUT。第二次重新执行整笔准备后成功，数据库存在唯一匹配回执。

这为显式三次传输尝试提供了实际阶段恢复证据，也暴露整笔准备时间的限制。不能据此宣称平均延迟下降、所有写入问题解决或总体准确率提高；它不是跨请求断点续跑，第二次 HTTP 会重新生成前序阶段。
