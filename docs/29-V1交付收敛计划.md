# Top 1：交付可维护的 Agent Memory V1

制定日期：2026-09-07。状态：当前候选已通过部署、恢复、长时托管和固定小集；37题长背景验收失败，全量与正式封版未完成。本计划是当前唯一交付主线，优先于历史文档中扩功能、扩大消融矩阵和反复追分的工作。

## 加速收尾：当前执行顺序

唯一最高优先级目标：交付可部署、可验证、可恢复、可继续迭代的V1。保持现有范围，不以首版准确率提升为封版前置条件；功能正确性与完整验收仍是前置条件。

| 顺序 | 必须完成的工作 | 完成边界 |
| --- | --- | --- |
| 1 | 关闭当前网络与长背景写入阻塞 | 先确认本机出网与最小模型生成恢复，再依据保存现场区分代码、模型输出和通信故障；仅修已确认原因，不加预算、不反复重试刷成功；19项历史终止写入形成明确关闭或合理拒绝证据 |
| 2 | 验收同一候选的固定闭环 | 复用已通过的小集及20项存储检查；代码或相关配置变更则重验。四个完整长背景37题候选/原文完成，合法写入通过，遗忘无泄漏、更新有效、邻居保留；真实长背景未通过前不启动1000题 |
| 3 | 冻结版本并完成一次完整评测 | 空库公开500+500题，1000条真实终态及审计；报告整体/条件准确率、失败类型、时延和成本，助手复核与人工标签分开，保留全部旧失败 |
| 4 | 发布并交接 | 固定三仓提交和镜像、推送私密仓库、导出源码/配置/结果归档、校验哈希、从包内递归克隆并部署，交付演示、备份恢复与回退说明；五项门槛全部通过才能称正式V1 |

可并行工作仅限现有交付清单、归档和文档整理。当前通过的部署与小集证据直接复用，只有相关变更才重新验证。无需增加新框架、新模型选型或全量重复实验。

交付分两步：先准备明确标注未通过门槛的候选交接包，确保源码和部署能力可接手；验收完成后发布正式V1。候选包不能被标为正式完成。基础设施恢复时间尚不确定，因此按上述验收里程碑推进，不承诺未经验证的封版日期。

保持可迭代的最小约束：三个HTTP接口稳定；模型调用集中在现有适配模块；准备与事务提交分离；数据格式有版本和恢复路径；每次变更有相关回归与同预算对照。正式V1之后再优化写入成本、长背景准确率与检索收益，每轮只改变一个主要因素，不提前搭建通用扩展框架。

## 交付目标

交付一个从干净环境可安装、可启动、可演示、可评测、可定位故障并可升级的项目。第一版保留赛题的三个 HTTP 接口、同步写入、用户隔离、记忆提取/存储/召回/更新/遗忘和基础时间处理。以可核验的工程完成度和真实效果报告验收，不承诺未测得的准确率或外部模型可用性。

原1000题评测已中断：LoCoMo 83/500；MemOps还有348题无结果。该轮永久保留为中断记录，不拼接成完整新成绩。历史331/1000保留。来源：[中断报告](../reports/round2-full-98c12e5-interrupted.md)。

## 一条主线，五个可验收工作包

### P0-1：修复阻塞，明确失败边界

实施起点为service `98c12e5`、eval `11da2a6`，在新候选提交中改动，不篡改旧实验身份。

- 对已保存19次终止写入逐项建立“预期行为—实际行为—原因—回归证据”映射，复用现有测试目录和保存现场。按错误类别修复，不按题号、姓名或答案特判。
- 首先处理缺状态码流错误的分类和传播、抽取/核验的可记忆性口径冲突、来源覆盖与擦除计划不一致、4次恢复不可继续的真实触发原因。保留对无来源事实、错误目标和非法删除的拒绝。
- 将模型预算与HTTP截止时间、可重试传输错误与语义拒绝分开。仍使用原请求ID和载荷，仍有次数/时间上限；不扩大重试直到成功，不提交未经核验的半成品。
- 在现有运行入口和部署方式中处理长任务托管，保存runner退出码/可观测终止信息，识别失活进程和陈旧manifest。用不消耗模型的验证覆盖超过本轮约两小时的运行窗口，以及父会话结束、正常停止和异常退出。SIGKILL等无法由子进程自报的情况由外部观察记录，取不到原因时保留unknown。
- 恢复边界明确：已提交请求重试返回唯一回执；未提交事务无半状态；同进程可继续的请求按现有有界机制恢复；进程重启丢失模型响应缓存时明确终止，不假装支持跨进程续跑。不为本版扩建持久化工作流。

完成证据：适用的服务/评测器测试通过；新增回归先复现再修复；每个已确认P0有原因及验证结果；无已知的串用户、重复提交、漏遗忘、误删邻居、错误成功或长任务无状态退出缺陷。正常输入与应拒绝输入分别验收，不能要求所有历史拒绝都改成成功。

### P0-2：整理唯一发布配置与交接入口

- 同步`.env.example`、Compose、Makefile和服务配置，明确开发、增强部署和离线运行的命令、模型前置条件及数据目录。增强模式不能静默变成离线成功。
- 保持`/add`成功立即可检索，服务不生成最终答案。最终证据上限保持32条/6000估算token；请求截止仍为add 115秒、search 55秒，落在赛题120/60秒约束内。
- 用已有结构化日志区分模型通信、语义核验、存储、请求超时和评测进程退出。普通日志记录请求关联、阶段、耗时、错误码和恢复结果；私有模型原文追踪单独开启，凭据不进入日志或交付包。
- README明确实际入口、已验证平台和当前版本，不继续把旧8088部署、旧测试数或331/1000当成新版本现状。提供一次完整写入/查询/更新/遗忘演示和故障排查路径。
- 明确离线方案的支持范围并独立验证；无法安全执行的复杂语义操作应明确失败，不能把离线模式标成增强模式等价替代。

完成证据：独立干净递归克隆可按文档构建；service无需eval运行时代码即可启动；契约测试通过；正常停止保留数据，重启后已提交记忆与遗忘状态不变；演示命令均由实际执行验证。

### P0-3：固定小集闭环与一次原文对照

- 保留已有2组10题控制集和20项存储检查，覆盖同步可见、用户隔离、更新、遗忘、邻居保留及否定/引用指令。
- 从已曝光数据预先固定最多4个真实长背景（LoCoMo与MemOps各2个），保留完整会话，选定合计不超过40个问题；覆盖已知失败及正常对照。名单、问题、预期行为和配置在候选运行前冻结。这是开发回归，不是新隐藏集。
- 复用已有原文B1与候选运行入口，分别空库执行一次完整闭环。同一数据、embedding、Answer/Judge、提示词、重试上限与最终证据预算；写入模型调用、实际证据量和耗时单独报告，不声称总计算量相同。
- 候选在固定范围内的预期合法写入与全部问题必须完成，禁止靠更换失败请求ID补分；应拒绝的负例必须正确拒绝。存储与检索中的遗忘泄漏、误删邻居为0，不能以Answer不复述旧值代替存储验收。
- 我先独立模型复核答案和典型失败，并披露复核方法；人工标签仍为0。人工空缺不阻止工程首版交付，也不写成“已完成人工校准”。

完成证据：固定小集闭环和操作检查通过，有逐题候选/原文对照、调用量及延迟报告。问答未超过原文基线也如实发布；不能据此关闭赛题必需的更新、遗忘与隔离。

### P0-4：冻结候选，完成一次1000题评测

前三项通过后，冻结三仓库提交、模型与提示词、配置、数据哈希和依赖，从空库启动一个新的独立评测实例。新实例用于验证新候选，原中断轮不恢复补分，也不覆盖历史记录。

- 使用现有500+500公开题及评分协议，保留完整背景灌入要求；不改变计分规则规避服务失败，不访问封存MemOps。
- 运行期间冻结代码、模型、预算和请求身份。1000题都需有按既定协议产生的终态；完整覆盖不等于全部进入判分。
- 报告正确/1000、已判分条件准确率、写入成功率、受影响背景、service/pipeline/judge错误、延迟与模型成本，以及相对历史结果的差异。已有错误可披露，不能携带已确认且未解决的P0缺陷发布正式版。
- 使用现有完成集审计验证两个finished manifest、1000题终态、HTTP白名单与载荷身份、评分代码和证据哈希。任何中断或缺失都不能发布完整分数；不把缺失记录伪造成完成。
- 不因准确率未上涨就开启下一轮算法改造。只有代码缺陷、基础设施故障或仍未解决的验收风险才触发相应修复与重新冻结，并完整保留旧结果。

完成证据：完整、审计通过的1000题报告。无需在V1前补做大规模消融、至少三次全量重复或统计显著性结论。准确率改善与重复实验进入后续迭代。

### P0-5：封版、干净部署和可恢复交付

- 更新现有打包/readiness脚本，使其按本次发布清单检查当前提交与证据。当前脚本含历史commit、旧测试数量和旧实验矩阵断言；不能直接用旧ready报告为新代码背书，也不能删除检查后将未验收版本标成ready。
- 首次候选包可标`v0.1.0-rc.1`并明确哪些门槛待完成；RC便于接手和部署，不称为正式完成。五项门槛通过后才发布正式V1，先检查仓库版本/tag是否已占用。
- 三仓库固定提交、镜像标识、依赖锁、配置模板、模型名称/digest、数据格式版本和结果哈希一致。私密仓库提交推送，保留Mem0来源说明与许可证。
- 复用bundle/package/verify流程，实际读取归档、校验SHA256，从包内递归克隆并启动验证。旧包和原始实验现场不覆盖；新包不夹带API key、私有模型原文追踪或运行数据库。
- 提供数据备份、恢复与升级说明。镜像回退必须与兼容的数据快照配套；新版本禁止静默打开不兼容的数据格式。

最终交付物：可递归克隆的版本、独立服务镜像/源码、配置模板、已实跑的部署与演示说明、测试和契约证据、完整评测与已知限制报告、可校验的归档、后续迭代清单。

## 如何保持可演进

| 稳定边界 | 后续变化方式 |
| --- | --- |
| HTTP契约 | 保持现有三个接口与权威schema；内部重构必须通过相同黑盒测试 |
| 模型适配 | 基于现有Models模块替换provider/model；统一错误、预算和响应校验，不散落调用 |
| 准备与提交 | 提案准备不直接写库，事务提交负责一致性；内部类型和负例回归固定行为 |
| 检索与证据预算 | 新召回/排序组件通过配置进入候选；保留当前简单路径和同预算回归 |
| 数据格式 | 版本检查、升级/重建说明、备份与回退成对验证；不默认为旧数据向前兼容 |
| 评测 | eval始终只用HTTP；同题同预算对照，完整分母、错误和来源身份保留 |
| CI与维护 | 复用两功能仓库现有CI做构建、类型、单元/契约检查；真实模型验收单独留证，不要求每次提交都跑1000题 |

不为“可演进”提前增加通用抽象。每个后续改动都要求问题、最小改动、相关回归和结果差异；更新完成边界后再发布补丁或次版本。

## 排序与停止扩张规则

1. 先修P0-1已确认的功能阻塞。无模型长任务验证后台运行期间，并行完成P0-2部署和配置验证，避免纯等待；门槛不减少。修复后形成可验收候选再运行固定小集。
2. 模型、算法、预算保持单一主配置，不并行试多套架构。只针对已确认的交付阻塞修复；未知问题先保存证据，不继续堆防御分支。
3. 小集通过后就转全量和封版，不继续扩大研究矩阵。完整评测只承担一次冻结版本的测量，不承担边跑边调参。
4. 任一门槛失败，只回到该工作包修复其原因。不能靠去掉遗忘、隔离、原子性、失败分母或审计来“加速完成”。尚未通过的版本维持RC状态。
5. 正式版后再排准确率优化、更多未曝光验证、统计重复、长期跨进程恢复和更大规模存储。后续清单保持有限，不阻塞已经验收的首版。
