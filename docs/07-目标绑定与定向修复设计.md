# 目标绑定与定向修复：真实失败驱动的下一阶段设计

状态：部分实施，完整设计仍未验收。稳定同chunk句柄、局部补丁修复、逐事实核验及确定性目标解析已落地；操作级结构化/词法候选扩展已实现，独立语义目标分类与向量/原文目标扩展仍待实施。证据为第二轮四个原始失败前缀，均属于已曝光回归数据。

当前核心问题是提取器同时负责“识别发生了什么”与“决定修改哪一条记录”。当不存在对应旧记录时，模型会把纠错绑定到可见但无关的m0；属性守卫可以阻止破坏，但整份JSON重生成仍可能重复相同错误。来源引用、同chunk顺序与删除范围又混在同一次生成中，使修复容易互相干扰。

```mermaid
flowchart LR
    A[原始消息和来源位置] --> B[事实与操作意图提取]
    B --> C[按主体、属性、对象生成候选]
    C --> D[独立目标解析]
    D --> E[来源与语义核验]
    E --> F[原子提交事实、原文可见性与事件]
    D --> G[类型化失败与定向修复]
    E --> G
    G --> C
```

## 需要改变的边界

1. **提取阶段不直接授予数据库修改权。** 操作意图包含动作、人物、对象、属性、范围和精确来源；在目标解析完成前，模型生成的ID只是候选建议。避免把“可见第一条记录”隐式当作默认目标。
2. **目标解析返回明确结果。** `resolved`给出租户内实际目标及逐目标依据；`unrecorded_correction`只适用于已证明为未入库助手错误的纠正，保留有用户原文支持的新事实；`ambiguous`、`missing_evidence`继续修复或拒绝。不得把所有找不到目标的forget都变为成功no-op。
3. **候选扩展按真实意图触发。** 首先查主体/属性/实体，必要时扩展词法与向量候选；只把确实相关的事实和原文送给绑定器。原文尚未形成事实时需要创建可追溯的来源目标，不能用一个experience大桶代替。扩展受统一请求预算与最大次数限制。
4. **稳定同chunk句柄。** 新事实句柄在拆分与修复中保持稳定，只有先于操作的来源可被绑定。修复不能重排数组后把new:N指向别的事实；未知/未来引用是类型化错误。
5. **定向修复不重生成无关内容。** 分开修复来源位置、候选引用、范围与遗漏事实。已验证的事实保持不变；修改的事实、依赖及操作再核验。核验格式错误可以有限重试，语义失败不能靠反复重判取通过结果。
6. **语义核验覆盖每条新事实。** 除已有的操作与消息覆盖检查，还要验证新事实是否由用户原文支持、是否把计划当已发生、是否把泛泛问题当个人属性。来源出现了同一个词不构成语义支持。

## 确定性目标解析已实施，长段核验仍需减小重复工作

`binding.ts` 返回resolved、missing_evidence或ambiguous。显式ID、属性选择器、重复表示及property遗忘边界统一解析；每个解析目标附带选择依据。提取后先解析并把完整目标交给独立语义核验，提交时用相同规则复核，不能在核验之后悄悄扩展出未检查的目标。缺失/未来目标不作为成功no-op。恢复或初始更新的空目标仍须满足原有授权/新事实要求。

目标找不到或范围不匹配时，按该操作的主体、属性、scope与引用文本，从租户快照追加至多32个候选，而不只复用原先按整段对话排名的120条。候选只是给定向补丁看的建议，不自动改绑ID。当前单操作核验目标上限为256条，超出时拒绝；大范围分组核验尚未实现。尚未接入语义向量扩展、原文目标，以及单独的unrecorded_correction证明类型。

性质不同的遗忘已分开：property边界覆盖同一主体/属性/scope的历史值与当前值；value边界只扩展同值重复表示。错误纠正的扩展以已选旧目标为准，不使用操作字段中的新值。源位置判断还拒绝同消息内不唯一的短引用。

真实失败说明，局部补丁之后仍全量核验会耗尽预算：C30只改一个content限定语，第二次核验仍重查整段；E03补回计划时又写错模态。下一步实施请求内的核验记录复用，必须满足：

1. 记录绑定请求原文、模型/协议版本、事实/操作内容及引用目标的哈希；不能放在多个租户共用的Models实例上。
2. 只复用结构合法、来源合法且语义通过的逐项结果。失败、歧义及格式错误不是通过记录。
3. 修改事实后，重验该事实、依赖/替换关系、受影响操作与消息覆盖；删除或重编号须使旧引用失效。所有新项目必须核验。
4. 为第二次核验传入完整原文上下文和提案，但只要求返回失效项目的检查；合并已通过记录后仍检查完整覆盖。不以省token为由删掉授权上下文。
5. 测试跨请求/租户隔离、记录伪复用、依赖变更、缺项与格式失败，再用原C30/E03失败输入验证。不能提高接口时限或只报告模型最好的一次结果。

### 请求内增量核验实现

`Extractor.prepare` 每次创建独立 `VerificationSession`。记录绑定请求全文、模型/协议身份、事实及操作内容、来源、目标和传递依赖的哈希；embedding变化不改变语义证据。修改或删除事实、调整索引、改变目标/依赖、添加项目都会使相应检查及消息覆盖失效。缺失或循环依赖明确拒绝，旧的并发计划不能向新计划提交核验结果。

只有完整协议校验成功后，逐项通过结果才进入私有内存表。协议错误不产生通过记录，已确认的语义拒绝仍保留；未修改的拒绝不能重抽样取得通过。`CHECK_SCOPE` 仅限制本次输出范围，完整原文、提案及传递目标上下文仍发送给模型。将本次结果和复用记录合并后，再运行唯一性、引文及完整覆盖检查，重复输出缓存项目或缺少新项目都会拒绝。

`MEMORY_INCREMENTAL_VERIFICATION=false` 关闭正向复用，用于同协议消融；拒绝记录和来源约束仍保留。补丁新增事实现在必须显式填写modality，提示说明未来意图即使表达坚定也保持tentative；局部编辑不把未提供的字段重置为默认值。

112项服务测试覆盖上述边界及真实Extractor调用链。[原C30记录的离线机制重放](../reports/round2-recorded-C30-verification-scope.json)中，修正fact0会连带重验fact1、纠错操作、替换关系和消息10/14：36项中6项重新检查，30项可复用。该探针没有新模型调用，不能据此声明真实延迟收益；最新完整前缀及对照结果另记于阶段状态报告。
